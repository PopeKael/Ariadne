# Ariadne Plugin Framework v0.1

This document defines the first, deliberately small plugin boundary for the
Ariadne personal assistant operating environment.

## Ariadne Core

Ariadne Core owns the Windows host and application lifecycle, tray, desktop
avatar, Home / Ask Ariadne, Knowledge Vault retrieval, identity and World
State, personality, model routing, plugin registry, configuration,
telemetry/health, GPU/resource arbitration, and security/permissions.

Core is the authority for user-facing presentation. A plugin must not select an
avatar image, animation, speech, tray action, or direct user notification.

## What a plugin is

A plugin is an optional capability that Ariadne can discover and, in a later
contract revision, invoke through a defined adapter. It may have a full UI,
settings only, a background service, callable capabilities, or more than one
of these. Capability and UI are separate.

Plugin Contract v0.1 is metadata-first at discovery time. The registry
validates manifests without importing or executing entry points. On-demand
execution is a separate Core boundary: trusted bundled adapters are resolved
only after session, action, enabled-state, configuration, and permission
checks. The first executable plugin is Cleanup, whose adapter invokes the
existing Downloads organiser.

## Manifest Contract v0.1

Each plugin is represented by a UTF-8 JSON file named `plugin.json`. The core
fields are:

| Field | Meaning |
| --- | --- |
| `manifest_version` | Contract version, currently `0.1`. |
| `plugin_id` | Stable lowercase identifier for the plugin. |
| `name`, `version`, `description`, `author` | Human-readable identity and semantic version. |
| `plugin_type` | `capability`, `service`, or `background`. |
| `capabilities` | Lowercase capability identifiers such as `document.analyze`. |
| `actions` | Optional declared on-demand actions such as `preview` and `apply`. |
| `action_metadata` | Optional per-action `{schedulable, mutating}` declarations for future trigger routing. |
| `entry_point` | Declarative adapter reference; not imported during discovery. |
| `ui` | `{available, route, label}` metadata for an optional local Ariadne page. |
| `settings` | `{available, route}` metadata for optional settings. |
| `permissions` | Core-recognised permission declarations. |
| `dependencies` | Other declared plugin identifiers or package dependencies. |
| `hardware_requirements` | Declarative hardware constraints. |
| `resource_requirements` | Declarative CPU/GPU/memory/storage expectations. |
| `startup` | `on_demand`, `background`, or `application`. |
| `enabled` | Manifest enabled state. |
| `health` | `{state, detail}` with `healthy`, `attention`, or `unavailable`. |
| `activity` | `{supported, transport, progress}` for the Core activity channel. |

Unknown top-level fields are rejected. This keeps the Core contract explicit
and prevents arbitrary plugin-specific metadata from becoming an accidental
Ariadne API.

## Host-facing activity events

Long-running work reports through `plugin_activity.PluginActivityReporter`.
The reporter writes structured, asynchronous events to Ariadne Core:

```json
{
  "event_id": "generated-by-core",
  "timestamp": "2026-08-26T03:00:00.000+00:00",
  "activity_id": "job-123",
  "plugin_id": "example.video",
  "capability_id": "video.generate",
  "state": "progress",
  "progress": 42.5,
  "stage": "rendering",
  "status_text": "Rendering the next scene."
}
```

`activity_id`, `plugin_id`, `capability_id`, and human-readable `status_text`
are required. `state` is one of `started`, `running`, `progress`, `stage`, `completed`,
`warning`, `failed`, or `cancelled`. `progress` is optional and, when present,
is a percentage from 0 to 100. `stage` is optional semantic text. Capabilities
that need Core presentation should prefer stable lowercase tokens such as
`preparing`, `reading`, `searching`, or `cross-referencing`; Core may map those
tokens to existing presentation states. Plugins must not emit avatar state
names or asset identifiers. Core timestamps and event IDs are generated by the
host.

Events are queued to a bounded background writer so a plugin can continue its
own long-running work without blocking the lightweight resident host. A small
recent status window is available to Core/UI. Activity logging is best effort:
storage failure or queue pressure cannot stop Ariadne or the plugin job.

The event stream is a status contract, not a presentation contract. Ariadne
may map `started` to its existing working state or `warning` to its warning
state, but plugins never refer to those avatar states directly. A capability's
`completed` event records that capability's work only; it does not imply that
the user's overall request is complete. For a standalone operational plugin
job, Core may map completion to the existing `success` state, then return to
normal idle handling. Core owns that presentation choice.

Core may pace the visual presentation of transient semantic stages. The
current host gives ordinary work states a short minimum dwell, presents
`reading` as a bounded roughly 800 ms cue that can return to the broader
request state, coalesces repeated or stale queued states, and lets warning,
failure, cancellation, speaking, and idle take priority. This pacing affects
only avatar rendering; events continue to arrive and plugin work continues
without delay. Future animated assets can use the same semantic state and
presentation timing boundary without exposing asset duration to plugins.

## Bundled and user-installed plugins

Bundled manifests live under the application-relative directory:

```text
control-plane/plugins/<plugin-directory>/plugin.json
```

User-installed manifests are discovered under:

```text
%LOCALAPPDATA%\Ariadne\plugins\<plugin-directory>\plugin.json
```

For development and tests, `ARIADNE_USER_PLUGIN_ROOT` may point to another
directory. The registry does not create or download either location. Bundled
and user manifests are both read-only discovery inputs for v0.1; duplicate
plugin IDs become an unavailable record rather than silently overriding one
another.

Malformed, incompatible, unreadable, or duplicate manifests become visible
`invalid` records and are skipped as providers. They cannot prevent Core from
starting. Discovery never imports a plugin module, starts a process, claims a
GPU, or opens a plugin UI. v0.1 execution is restricted to trusted bundled
adapter modules; user-installed manifests remain inventory/configuration
records until a stronger installation and sandbox contract exists.

## Capability identifiers

Capability identifiers belong to the plugin contract, not to a page-specific
button. Core can ask the registry which enabled providers supply an identifier:

```python
PLUGIN_REGISTRY.providers_for("video.generate")
```

This enables future generic routing without adding `if video_generator` and
`if music_generator` branches to Home. Declared executable actions use the
generic `POST /api/plugins/{plugin_id}/run` route and the existing session job
polling route. Core records the trigger (`manual` today; `scheduled` is
reserved for future scheduling) on the job. `action_metadata` is advisory
routing metadata, not authorization: a future scheduled `apply` must obtain
explicit user authorization at execution time and must never silently reuse a
saved UI confirmation. v0.1 does not provide a scheduler service or an
arbitrary third-party execution sandbox.

## UI versus background plugins

`ui.available` and `settings.available` describe optional local Ariadne routes.
The Plugins / Capabilities page only shows Open or Settings actions when a
manifest supplies the corresponding local route. A plugin with no UI is shown
as a background capability and is not presented as a fake application
launcher.

## Lifecycle, failure, and isolation

Discovery, metadata validation, activity reporting, and invocation are
separate failure boundaries. A plugin may be absent, disabled, incompatible,
unhealthy, or crashed. In each case Core keeps operating, reports the provider
as unavailable/attention, and falls back to the next provider or the normal
Core path where one exists. A plugin must not be allowed to take down the
resident host, avatar, tray, Home, Vault, or GPU governor.

The v0.1 registry deliberately does not load arbitrary entry points. Core's
current execution seam enforces trusted bundled adapter loading, declared
action checks, session ownership, confirmation for destructive actions,
bounded worker/process lifetime, cancellation, and exception-to-activity
translation before invoking a process. Plugin activity is the only host
status channel; direct avatar or notification calls are outside the contract.

## Minimal plugin manifest

```json
{
  "manifest_version": "0.1",
  "plugin_id": "example.research",
  "name": "Example Research",
  "version": "0.1.0",
  "description": "A bounded local research capability.",
  "author": "Example Developer",
  "plugin_type": "capability",
  "capabilities": ["research.web"],
  "entry_point": "example_research:Plugin",
  "ui": {"available": false, "route": null, "label": null},
  "settings": {"available": false, "route": null},
  "permissions": ["network.request"],
  "dependencies": [],
  "hardware_requirements": {},
  "resource_requirements": {"execution": "on_demand"},
  "startup": "on_demand",
  "enabled": true,
  "health": {"state": "healthy", "detail": "Ready"},
  "activity": {"supported": true, "transport": "ariadne-core", "progress": true}
}
```

A future developer should add the manifest under the bundled or user plugin
root, implement the adapter behind the declared entry point, use a Core-owned
activity reporter for progress, and add focused contract tests. They should
not edit the Plugins page to add a hand-maintained card.
